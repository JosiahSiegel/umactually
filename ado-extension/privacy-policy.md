## Data collection

The UmActually extension does **not** collect telemetry. The
extension is a thin wrapper around the UmActually CLI. The CLI:

1. Receives the PR diff from the Azure Pipelines agent (via the
   `System.AccessToken` build service identity, never via a user
   identity).
2. Redacts high-confidence secret patterns from the diff.
3. Sends the redacted diff to the user-configured
   `UMACTUALLY_API_URL` provider endpoint.
4. Posts the provider's response as inline review threads on the
   PR (via the same build service identity).
5. Writes the raw provider response to the user-configured
   `outputArtifact` path (default
   `artifacts/manual/s4-azure-mocked-run.json`).

The publisher's servers are not involved in any of these steps.
The publisher does not see the diff, the provider response, the
review threads, or the artifact.

## Data retention

The publisher does not retain any data generated by the
extension. The artifact is stored in the user's Azure DevOps
organization per the standard `PublishPipelineArtifact@1`
retention policy. The provider endpoint is the user's choice
and is governed by the provider's own retention policy.

## Third-party services

The extension calls the user-configured `UMACTUALLY_API_URL`.
That endpoint is the user's choice — common choices include
Anthropic's API, OpenAI's API, GitHub Copilot, or a self-hosted
LLM gateway. Use of that endpoint is governed by the provider's
own terms of service and privacy policy. The publisher is not a
party to that contract.

## Permissions

The extension requests the following Azure DevOps scopes in
`vss-extension.json`:

- `vso.build_execute` — queue and run the review pipeline
- `vso.code` — read PR diff and metadata
- `vso.code_write` — post review comments
- `vso.threads_full` — post PR threads

The extension does **not** request elevated scopes
(`user_impersonation`, `vso.code_manage`, etc.). All operations
are performed under the pipeline's build service identity.
